# Ask SOS StaySafe: assistant specification

Status: **demonstration mode** (live on the site). A connected AI service is **not built** and needs the approvals listed in section 6 first.

## 1. What runs today (demonstration mode)

- The assistant is built by `site.js` and opens from the "Ask SOS StaySafe" button on every page.
- Its answers come only from `assistant.json`. This file holds text already published on the seven pages, in six languages. It is generated by `build_assistant.py`, so the assistant can never say something the website does not say.
- Matching runs in the browser. Keywords are scored against the question, and the best entry above a threshold wins.
- Safety checks run **before** matching, in this order:
  1. **Danger words** (for example "kill myself", "in danger", in all six languages). The assistant shows the emergency message: go to a safe place, contact local emergency services or a trusted adult, and "I am an automated assistant and I can't send help". No SpeakUp link is shown here, because a written report is not the right first step in an emergency.
  2. **Disclosure words** (for example "my stepfather hits me"). The assistant shows the disclosure message, which:
     - thanks the person and says they deserve to be safe and heard;
     - gives the danger advice;
     - says they can talk to a trusted adult or the safeguarding person or team;
     - links to SOS SpeakUp;
     - says it is automated and can't take reports or contact anyone.
  3. **Email address or phone number typed.** The assistant reminds the person not to share personal details.
- **Privacy:**
  - Nothing typed is stored, logged or sent anywhere.
  - There are no cookies and no analytics.
  - The only thing saved in the browser is the language choice.
  - When the conversation panel closes, the conversation is gone.
- **Fallback:** if no entry matches, the assistant says it doesn't have enough approved information. It suggests asking another way or looking through the pages, and speaking to a trusted adult or a safeguarding focal point.

## 2. Safety rules (apply to any future version)

The assistant must:

1. Never ask for a name, age, location, school, photos, or details of what happened.
2. Never promise confidentiality and never say a report has been made, sent or received.
3. Never investigate, judge whether abuse happened, or give legal or medical advice.
4. Always say it is automated when asked, and in every safety message.
5. Put safety first. The danger message comes before anything else, and the disclosure message comes before any answer.
6. Answer only from approved SOS StaySafe content. If the content does not cover the question, say so and point to the pages, a trusted adult, or SpeakUp.
7. Use the official SpeakUp address only: `https://soscvi.speakup.report/en-GB/databreach/home`.
8. Be reviewed by the safeguarding team before any change to the safety messages or keywords.

## 3. Proposed connected version (not built)

The aim is to understand more ways of asking questions, while still answering only from approved content.

```
Browser (site.js)
   │  question text only (no identifiers, no history beyond the open panel)
   ▼
SOS-controlled endpoint (server, e.g. Azure Function / Cloudflare Worker)
   1. Rate limit and size limit (e.g. 500 characters, 20 questions per 10 minutes per connection)
   2. Same safety checks as today (danger, disclosure, personal details) run FIRST, server-side
   3. Retrieve the 3–5 most relevant passages from approved content (assistant.json / page text)
   4. Call the AI model with: system rules (section 2) + passages + the question
   5. Check the reply: it only links to the seven pages or SpeakUp, contains no promises,
      and contains no requests for details; otherwise send the fallback message
   ▼
Browser shows the reply, with links to the source page
```

### Requirements

- **API keys stay on the server** in its secret store. They are never in the HTML, `site.js`, the GitHub repository or any config file in the repository.
- **No retention.**
  - Questions and replies are not written to logs, databases or analytics.
  - Error logs record only status codes and timings.
  - The AI provider must contractually not store or train on the data. Use zero-retention options and confirm this in the data processing agreement.
- **Data location:** choose a region acceptable to SOS data protection (for example the EU).
- **The browser sends** only the question and the language code. It sends no IP-based identifiers to the model and no conversation ID that is kept.
- **Demonstration mode stays as the fallback.** If the endpoint fails, the browser answers from `assistant.json` as today.
- **The privacy policy must be updated before launch.** Today it says the assistant sends nothing anywhere.

## 4. Operational notes (estimates to confirm with IT)

| Item | Estimate |
|---|---|
| Hosting | Serverless function. Low cost at this site's traffic. |
| Model cost | Small model with short prompts (passages and question, under about 2,000 tokens). Typically a fraction of a US cent per question. Confirm with current provider pricing. |
| Maintenance | Rebuild `assistant.json` whenever page text changes. Review the safety keywords every quarter with the safeguarding team. |
| Monitoring | Counts only: number of questions, number of safety messages shown, error rate. No question text. |

## 5. Privacy implications

- Young people may type disclosures. The design treats every question as potentially sensitive. This is why nothing is kept and why the safety checks run first, before the AI model sees anything.
- A Data Protection Impact Assessment (DPIA) is needed before the connected version launches.

## 6. Approvals needed before building the connected version

1. Safeguarding team: the safety rules, the messages and the keyword lists.
2. Data protection officer: the DPIA, the data processing agreement with the AI provider, the data region, and the privacy policy update.
3. ICT: provider choice, hosting, secret management and the security review.
4. Communications: tone and branding of the replies.
